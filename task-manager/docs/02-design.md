## 2-1. 要件から「画面・データ・操作」を書き出す

お題の文章から、名詞と動詞を拾う。

> チームのタスクを管理する。タスクには**優先度・ステータス・期限**があり、**期限切れ**がひと目で分かる。
> 一覧に加えて、ステータスごとの**ボード**でも確認できる。データはブラウザを閉じても残る。

### 画面（URL）

| 画面   | URL      | 載せるもの                               |
| ------ | -------- | ---------------------------------------- |
| 一覧   | `/tasks` | 集計・絞り込み・並び替え・タスクのカード |
| ボード | `/board` | ステータスごとの 3 列                    |

追加・編集は「一覧の上にモーダルで出す」ことにした。ページを分けない理由は、入力項目が少なく、一覧を見ながら追加したいから（項目が多い・URL を共有したいならページに分ける。[在庫管理](../../inventory/) はページで作っている）。

### データ（型）

```ts
type Task = {
  id: string; // 重複しない id（crypto.randomUUID()）
  title: string;
  description: string; // 任意。未入力は ""
  status: "todo" | "doing" | "done";
  priority: "high" | "medium" | "low";
  dueDate: string; // "2026-10-03"。期限なしは ""
  createdAt: string; // "2026-10-03T09:00:00.000Z"
  updatedAt: string;
};
```

決め方のポイント：

| 決めたこと                                       | 理由                                                                                      |
| ------------------------------------------------ | ----------------------------------------------------------------------------------------- |
| 任意の項目も `""` で持つ（`undefined` にしない） | フォームの入力欄は空のとき `""` になる。型をそろえると変換が要らない                      |
| 日付は `Date` ではなく文字列                     | localStorage（JSON）に `Date` は保存できない。`"YYYY-MM-DD"` は文字列のまま大小比較できる |
| 選択肢は英語の値 ＋ 日本語の表示名               | 表示名を変えても保存データに影響しない。型（`TaskStatus`）で打ち間違いに気付ける          |
| `createdAt`・`updatedAt` を持つ                  | 「作成順」の並び替えに使う。あとから「更新順」も作れる                                    |

### 操作

| 操作               | どこから                             |
| ------------------ | ------------------------------------ |
| 追加・編集         | モーダル                             |
| 削除（確認つき）   | カード                               |
| ステータス変更     | カードのセレクト・ボードの移動ボタン |
| 完了をまとめて削除 | 一覧の下                             |
| 絞り込み・並び替え | 一覧・ボードの上                     |

この 3 つの表が、そのまま [5. 実装手順](05-implementation.md) の順番になる。

## 2-2. 状態をどこに置くか

「状態」とは、変わる値のこと。**置き場所を間違えるのが、いちばん多い設計ミス**。次の順に考える。

```text
その値は、ほかの値から計算できる？ ──はい→ 状態にしない（毎回計算する）
        │いいえ
        ▼
再読み込み・URL の共有をしても残したい？ ──はい→ URL（?status=done）か、persist した store
        │いいえ
        ▼
離れた複数のコンポーネント・ページで同じ値を使う？ ──はい→ Zustand の store
        │いいえ
        ▼
そのコンポーネントの中だけ ──→ useState（フォームなら React Hook Form）
```

このアプリでの判断：

| 値                             | 置き場所                     | 理由                                                 |
| ------------------------------ | ---------------------------- | ---------------------------------------------------- |
| タスクの一覧                   | Zustand（persist）           | 一覧・ボード・モーダルで共有し、再読み込みしても残す |
| 絞り込み・並び順               | Zustand（persist）           | 一覧とボードで共有し、前回の設定で開きたい           |
| 表示するタスク（絞り込み後）   | **計算**（`filterTasks()`）  | タスクと条件から求められる                           |
| 件数・期限切れの数・完了率     | **計算**                     | 同上。保存すると、タスクを変えたときに更新し忘れる   |
| モーダルの開閉・編集中のタスク | `useState`（カスタムフック） | そのページの中だけで使う                             |
| フォームの入力値・エラー       | React Hook Form              | フォームの中だけで使う                               |
| 削除の確認ダイアログの開閉     | `useState`                   | そのボタンの中だけで使う                             |

> **計算できる値は保存しない**。保存すると「元の値」と「計算した値」の 2 か所を同時に直す必要が出て、片方を忘れたときに表示がずれる。

## 2-3. なぜ Zustand を使うのか

`useState` は、そのコンポーネント（と props で渡した子）でしか使えない。一覧ページとボードの両方でタスクを読み書きしたいので、**コンポーネントの外に置く場所**が必要になる。

| 方法                             | 向いている場面               | このアプリで選ばなかった理由                                 |
| -------------------------------- | ---------------------------- | ------------------------------------------------------------ |
| 親に state を置いて props で渡す | 親子など近い場所             | ページをまたぐと、App まで持ち上げて全ページに配ることになる |
| Context ＋ useReducer            | ライブラリを足したくないとき | Provider で包む・値が変わると中の全員が再描画される          |
| **Zustand**                      | 離れた場所で同じ値を使う     | Provider 不要。使う値だけを選べる。persist で保存もできる    |

Zustand の store は「値」と「値の変え方（action）」をまとめたもの。画面は `addTask(input)` を呼ぶだけで、配列をどう変えるかは知らなくてよい。

```tsx
const tasks = useTaskStore((state) => state.tasks);       // 値を選ぶ
const addTask = useTaskStore((state) => state.addTask);   // action を選ぶ
addTask({ title: "議事録", … });                           // 呼ぶだけ
```

## 2-4. なぜ FSD でフォルダを分けるのか

FSD（Feature-Sliced Design）は「何を・どこに置くか」のルール。ルールがあると、

- ファイルを探すとき、置くときに迷わない
- 「どこから使われているか」が層で分かるので、直すときの影響範囲が読める
- 採点者・チームの人が、初めて見ても構成を理解しやすい

### 層と、このアプリのファイル

上の層は下の層を使ってよいが、**下の層から上の層は使わない**（`entities` は `features` を知らない）。

| 層         | 役割                             | このアプリの例                                                                |
| ---------- | -------------------------------- | ----------------------------------------------------------------------------- |
| `app`      | アプリ全体の設定                 | ルーティング（App.tsx）、Provider、全体の枠（RootLayout）                     |
| `pages`    | URL 1 つ分の画面。組み立てるだけ | `task-list`（一覧）、`task-board`（ボード）                                   |
| `widgets`  | entities ＋ features の大きな UI | `task-list`（カードの一覧＋操作）、`task-board`（3 列）                       |
| `features` | ユーザーの操作 1 つ              | `task-form`（追加・編集）、`delete-task`、`change-task-status`、`task-filter` |
| `entities` | 扱う「もの」                     | `task`（型・store・期限切れの判定・カード・バッジ）                           |
| `shared`   | 業務に関係ない共通のもの         | `ui`（部品）、`lib`（日付）、`config`（localStorage のキー）                  |

### 迷ったときの決め方

| これは…                                        | 置き場所                |
| ---------------------------------------------- | ----------------------- |
| タスクの型・store・「期限切れか」のような判定  | `entities/task/model`   |
| タスクの見せ方（操作ボタンなし）               | `entities/task/ui`      |
| 「削除する」「追加する」など、ボタンやフォーム | `features/<操作の名前>` |
| 2 つ以上の features を並べた部品               | `widgets`               |
| URL 1 つ分の画面                               | `pages`                 |
| タスクに関係なく、どのアプリでも使えるもの     | `shared`                |

### 守ること

1. **同じ層の別フォルダは import しない**：`features/delete-task` から `features/task-form` は使わない。両方使いたいなら上の層（widgets・pages）で並べる
2. **外からは `index.ts` 経由で使う**：`import { useTaskStore } from "@/entities/task"`。`@/entities/task/model/taskStore` と中まで書かない
3. **entities の UI は操作を持たない**：[TaskCard](../src/entities/task/ui/TaskCard.tsx) はボタンを `actions` で外から受け取る。一覧とボードで違うボタンを付けられる

## 2-5. なぜ React Hook Form ＋ zod なのか

`useState` でフォームを書くと、入力欄ごとに state と onChange、送信時のチェック、エラーの state…と増えていく。

| 困りごと                           | React Hook Form ＋ zod では                                |
| ---------------------------------- | ---------------------------------------------------------- |
| 入力欄ごとに state が要る          | `{...register("title")}` を渡すだけ                        |
| 1 文字ごとに画面全体が再描画される | 入力中は再描画されない（ブラウザに値を持たせる）           |
| チェックの if 文が散らばる         | zod のスキーマ 1 つにまとまる。エラー文もそこに書く        |
| 型とチェックが二重になる           | スキーマから型を作れる（`z.infer`・`z.input`・`z.output`） |

zod はフォーム以外でも使う。localStorage から読んだデータが正しい形かのチェックにも同じスキーマ（`taskSchema`）を使っている。

## 2-6. なぜ CSS Modules ＋ CSS 変数なのか

| 書き方                     | 理由                                                                       |
| -------------------------- | -------------------------------------------------------------------------- |
| 部品ごとの `*.module.css`  | クラス名が自動で一意になる。`.title` のような短い名前でもぶつからない      |
| 値は `var(--space-4)` など | 色・余白がそろう。数値を直接書かないので、見た目の調整が tokens.css で済む |
| 状態は `data-*` 属性で渡す | `data-done="true"` のように HTML に状態が出て、CSS でもそのまま使える      |

```tsx
<article className={styles.card} data-done={task.status === "done"}>
```

```css
.card[data-done="true"] {
  opacity: 0.6;
}
```
