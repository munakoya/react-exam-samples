# 6. 実装時の考え方とつまずき

> [目次](README.md) ｜ 前：[5. 実装手順](05-implementation.md)

## 6-1. 試験の進め方

### 最初の 10 分：作る前に決める

1. 要件を**チェックリストに書き写す**（必須と発展を分ける）。README に貼ると提出物にもなる
2. 画面・データの型・操作を書き出す（[2-1](02-design.md#2-1-要件から画面データ操作を書き出す)）
3. 実装の順番を決める：**表示 → 追加 → 編集 → 削除 → 絞り込み → 見た目**

### 進め方の原則

| 原則                                 | 理由                                                                           |
| ------------------------------------ | ------------------------------------------------------------------------------ |
| 動く最小のものから作る               | 見た目が整っていても、追加できなければ評価されない                             |
| 1 機能ずつ作り、動かしてからコミット | 途中で壊れても、直前のコミットに戻れる。履歴が「考えて作った順番」の証拠になる |
| 必須をすべて終えてから発展へ         | 発展が 1 つできても、必須が 1 つ欠けている方が評価は下がりやすい               |
| 見た目の調整は最後                   | CSS は時間が溶けやすい。まず部品（shared/ui）のままで機能を作る                |
| 詰まったら 15 分で区切る             | 別の機能を先に進め、あとで戻る                                                 |

### 時間配分の例（3 時間の場合）

| 時間       | やること                                                       |
| ---------- | -------------------------------------------------------------- |
| 0:00〜0:15 | 要件の書き出し・設計                                           |
| 0:15〜0:30 | 環境構築（[1 章](01-setup.md)）                                |
| 0:30〜2:00 | 必須機能（[5 章](05-implementation.md) のステップ 2〜6）       |
| 2:00〜2:30 | 発展機能                                                       |
| 2:30〜2:50 | 空・エラーの表示、スマホ幅、見た目                             |
| 2:50〜3:00 | 提出前のチェック（[6-5](#6-5-提出前のチェックリスト)）、README |

## 6-2. 迷ったときの判断基準

### これは state にする？

| 質問                               | 答え                                    |
| ---------------------------------- | --------------------------------------- |
| ほかの値から計算できる？           | できるなら state にしない。毎回計算する |
| そのコンポーネントの中だけで使う？ | `useState`                              |
| 離れた場所・別のページでも使う？   | Zustand の store                        |
| 再読み込みしても残す？             | persist した store、または URL          |
| フォームの入力値？                 | React Hook Form                         |

### コンポーネントを分ける？

分けるのは次のどれかに当てはまるとき。当てはまらないなら、無理に分けなくてよい。

- 2 か所以上で使う（TaskCard：一覧とボード）
- 自分の state を持つまとまり（DeleteTaskButton：確認ダイアログの開閉）
- 1 ファイルが長くなり、名前を付けると読みやすくなる

### どの層に置く？

| 迷っているもの                           | 置き場所                |
| ---------------------------------------- | ----------------------- |
| 判定の関数（期限切れか、在庫が少ないか） | `entities/<もの>/model` |
| 操作のないカード・バッジ                 | `entities/<もの>/ui`    |
| ボタン ＋ 確認ダイアログ、フォーム       | `features/<操作>`       |
| 複数の features を並べた一覧             | `widgets`               |
| 1 画面でしか使わない、小さな表示         | その `pages/<画面>/ui`  |
| 日付の整形など、業務に関係ない関数       | `shared/lib`            |

迷ったら「下の層に置けるか」を考える。下に置けるもの（ほかの層を知らなくても書けるもの）ほど使い回しやすい。

### 名前の付け方

| もの                   | 付け方                  | 例                                    |
| ---------------------- | ----------------------- | ------------------------------------- |
| コンポーネント         | 名詞・大文字始まり      | `TaskCard`・`DeleteTaskButton`        |
| 関数・action           | 動詞から                | `addTask`・`filterTasks`・`isOverdue` |
| 真偽値                 | `is`・`has`・`can` など | `isOverdue`・`hasError`               |
| store のフック         | `use〇〇Store`          | `useTaskStore`                        |
| イベントを受ける props | `on〇〇`                | `onEdit`・`onClose`                   |
| 選択肢の配列・表示名   | 複数形・`〇〇Labels`    | `taskStatuses`・`taskStatusLabels`    |

## 6-3. よくあるバグと直し方

| 症状                                                     | 原因                                                           | 直し方                                                                                                             |
| -------------------------------------------------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| 画面が固まる・「Maximum update depth exceeded」          | Zustand のセレクターで `filter`・`map`・`{…}` を返している     | 元の値を選んでから計算する。複数なら `useShallow`（[4-3](04-libraries.md#4-3-zustand)）                            |
| store を変えたのに画面が変わらない                       | 元の配列・オブジェクトを書き換えている（`push`・`task.x = …`） | スプレッド構文で新しく作る（[3-3](03-modern-js.md#3-3-スプレッド構文-コピーして一部を変える)）                     |
| 並び替えたら、元の一覧の順番まで変わった                 | `sort()` が store の配列を書き換えた                           | `toSorted()` か `[...tasks].sort()`                                                                                |
| モーダルを開くと前回の入力・エラーが残っている           | `defaultValues` は最初の 1 回だけ使われる                      | 開くたびに `reset(初期値)`、または `key` を変えて作り直す                                                          |
| 編集フォームに前のタスクの値が出る                       | 同上                                                           | 同上                                                                                                               |
| 送信ボタンを押しても何も起きない                         | `type="submit"` がない／`<form>` の外にある                    | `type="submit"`。外なら `form={formId}` で結びつける                                                               |
| 数値の入力が `"3"` の文字列で届く・NaN のエラー          | `valueAsNumber` を付けていない／空欄                           | `register("x", { valueAsNumber: true })` ＋ `z.number({ error: "…" })`                                             |
| 一覧に `0` と表示される                                  | `{tasks.length && …}` の 0                                     | `{tasks.length > 0 && …}`                                                                                          |
| 「Each child in a list should have a unique key」        | `map` の要素に `key` がない                                    | `key={task.id}`                                                                                                    |
| 型を変えたら画面が真っ白・データが消えた                 | localStorage に古い形のデータが残っている                      | DevTools → Application → Local Storage で消す。残すなら `version` ＋ `migrate`                                     |
| 「今日」が 1 日ずれる                                    | `toISOString()` は UTC                                         | 地域の日付で作る（`todayString()`）                                                                                |
| `navigate` のあとに store を変えたら、別のページに飛んだ | ページの移動が遅れて反映された                                 | `<BrowserRouter useTransitions={false}>`（[4-2](04-libraries.md#ページの移動と-store-の更新の順番usetransitions)） |
| `@/…` の import で「見つからない」                       | エイリアスを vite.config か tsconfig の片方にしか書いていない  | 両方に書く（[1-5](01-setup.md#1-5--で-import-できるようにするパスエイリアス)）                                     |
| フックのエラー（Rendered more hooks than…）              | `if` の中・early return の後でフックを呼んでいる               | フックはコンポーネントの一番上にまとめる                                                                           |

## 6-4. 動かないときの調べ方

1. **ブラウザのコンソール**（F12 → Console）：赤いエラーの 1 行目と、ファイル名・行番号を見る
2. **`npm run build`**：型のエラーをまとめて出せる。`npm run dev` は型エラーがあっても動いてしまう
3. **値を出してみる**：`console.log(tasks)`。直したら消す
4. **localStorage**：DevTools → Application → Local Storage で、保存された中身を見る・消す
5. **React DevTools**（拡張機能）：コンポーネントの props・state を見る
6. **zod のエラー**：`schema.safeParse(value)` の `error` を `console.log` すると、どの項目が合わないか分かる
7. **最小にする**：怪しい部分をコメントアウトして、どこから壊れるかを絞る。直前のコミットとの差分（`git diff`）も見る

## 6-5. 提出前のチェックリスト

### 機能

- [ ] 要件のチェックリストがすべて埋まっている
- [ ] 追加・編集・削除のあと、**再読み込みしても**残っている
- [ ] 0 件のとき・条件に合うものがないとき・見つからないとき（存在しない URL）の表示がある
- [ ] 入力エラーで止まり、正しく直せば送信できる
- [ ] 削除の前に確認が出る

### 見た目・使いやすさ

- [ ] スマホ幅（DevTools の端末表示、幅 375px ほど）で崩れない・横にはみ出さない
- [ ] ボタンや入力欄にラベルがある。アイコンだけのボタンに `aria-label` がある
- [ ] キーボード（Tab・Enter・Esc）でも操作できる

### コード

- [ ] `npm run build` と `npm run lint` がエラーなしで通る
- [ ] コンソールにエラー・警告が出ていない
- [ ] `console.log` や仮データのボタンを消した
- [ ] 使っていない import・ファイルがない

### 提出物

- [ ] コミットが機能ごとに分かれている（最後にまとめて 1 コミットにしない）
- [ ] README に「動かし方（`npm install` → `npm run dev`）」「できること」「工夫した点・できなかった点」を書いた
- [ ] `node_modules`・`dist` をコミットしていない

### README に書くとよいこと

```md
## 動かし方

npm install
npm run dev

## できること

- タスクの追加・編集・削除（モーダル）
- …

## 工夫した点

- タスクの一覧と、絞り込みの設定を別の store にした（データと表示の設定を分けるため）
- 件数や完了率は保存せず、タスクから計算している（更新し忘れを防ぐため）

## できなかった点・次にやりたいこと

- ドラッグでボードの列を移動する
```

「工夫した点」は**なぜそうしたか**まで書くと、考えて作ったことが伝わる。
